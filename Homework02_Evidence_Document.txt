1. PROJECT OVERVIEW (HOW THE APP WORKS)
--------------------------------------------------------------------------------
This app is a real-time message board built with Flutter and Firebase. 
Here is how it is structured in plain English:

- Splash Screen: When you open the app, it initializes Firebase. If there is a 
  connection problem, it shows a simple Retry button.
- Authentication (AuthService): Users can sign up with an email and password or 
  log in. Firebase Auth handles passwords securely.
- User Profile Record (UserService): When a user registers, we save their 
  account info in a Cloud Firestore document under "users/{uid}". It saves:
  1. uid (user ID)
  2. firstName
  3. lastName
  4. role (Student, Faculty, or Staff)
  5. registrationDateTime (server timestamp)
- Profile Gate (ProfileGate): Once logged in, this screen makes sure the user 
  actually has their 5-field profile saved in the database before sending them 
  to the board. If the profile is missing (for example, if the internet dropped 
  during sign up), it lets the user fill in their name and save it so they never 
  get stuck.
- Live Board (BoardService & BoardScreen): Shows all messages ordered from 
  oldest to newest. It uses Firestore snapshots(), so when anyone posts a 
  message, it pops up on everyone's screen instantly without pressing refresh.
- Ownership & Editing: You can edit or delete your own posts. Other people's 
  posts do not show edit or delete buttons.
- Security Rules (firestore.rules): Even if someone tries to bypass the app 
  and send raw database requests, Firestore rejects any attempt to edit or delete 
  another person's message with a "permission-denied" error.

2. FIRESTORE DATA MODEL (WHO WRITES WHAT)
--------------------------------------------------------------------------------
We keep private user info separate from public message board posts:

1. Path: users/{uid}
   - Fields: uid (string), firstName (string), lastName (string), role (string), 
     registrationDateTime (server timestamp).
   - Who writes it: The user who created the account, exactly once when signing up.
   - Who can see it: Only the owner (request.auth.uid == uid). No other user 
     can read your private profile document.

2. Path: messages/{msgId}
   - Fields: text (string), authorUid (string), authorName (string), 
     createdAt (server timestamp), editedAt (server timestamp, optional).
   - Who writes it: Any logged-in user who posts a message.
   - Who can see it: Any logged-in user can read all messages on the board.
   - Who can update/delete: Only the original author (authorUid == request.auth.uid).

Why this matters:
The server clock (FieldValue.serverTimestamp()) is used instead of the phone's 
clock. A user's phone clock can be wrong, changed manually, or set to a different 
timezone. The server timestamp ensures all messages appear in the true order they 
were sent.

4. CRITICAL THINKING CASE FILES
--------------------------------------------------------------------------------

Case File 1: The Ghost Editor
- The Situation: A message board app copied simple rules (allow read, write: if request.auth != null;). 
  In the demo, everyone only edited their own posts because the buttons were hidden 
  for other users' posts. But weeks later, students were able to edit and delete 
  each other's messages.
- Diagnosis: Hiding a button in the Flutter UI is just design (UX), NOT security. 
  Authentication means proving who you are (having a valid login token). Authorization 
  means checking if you have permission to touch this specific document. 
  Because the old rule allowed ANY signed-in user to write to any message, someone using 
  a simple web tool like Postman could send an update to any message ID and Firestore 
  would allow it.
- The Fix: In firestore.rules, we enforce ownership at the database level:
    allow update, delete: if request.auth != null 
                          && resource.data.authorUid == request.auth.uid;
- Trade-off: Normal users can no longer edit other people's posts. If an administrator 
  needs to moderate or remove bad posts, that must be done using a secure backend 
  (like a Firebase Cloud Function with Admin privileges), not regular client code.
- How to Prove It: Log in as User A. Try to run an update on User B's post. The database 
  immediately throws FirebaseException with code "permission-denied".

Case File 2: The Runaway Dupes
- The Situation: Students on slow campus Wi-Fi kept getting double posts—two identical 
  messages appearing minutes or hours apart.
- Diagnosis: When network connection is bad, two things happen:
  1. The user thinks nothing happened because the screen didn't update, so they tap 
     Post a second time.
  2. Firestore has offline caching. When you call collection.add(), it saves the 
     write locally and tries to send it. If the phone loses connection, the SDK 
     queues the request. When connection comes back, if the user already retried, 
     both requests get sent, creating two separate documents with two different random IDs.
- The Fix:
  1. Disable the Post button the exact millisecond it is pressed (_posting = true).
  2. Use a unique message ID (like authorUid + timestamp or UUID) with doc(id).set() 
     instead of random collection.add(). If the write gets retried twice, it just 
     updates the same document once instead of creating two separate posts.
- Trade-off: It takes a little more code to generate unique keys, but it completely 
  stops duplicate messages from showing up on slow internet.

6. REFLECTION QUESTIONS
--------------------------------------------------------------------------------

Prompt 1: What did you expect vs what actually happened?
I expected Firebase Authentication and Cloud Firestore to work as one single system. 
In reality, they are two separate services. You can successfully create a login account, 
but the database write can still fail if the rules or internet aren't right. That's why 
we have ProfileGate to make sure the profile is actually saved.

Prompt 2: What was a bug you had to fix, and how did you fix it?
When building the release APK, the app couldn't talk to Firebase because the release 
build didn't have internet access enabled in Android. 
Fix: I opened android/app/src/main/AndroidManifest.xml and added:
<uses-permission android:name="android.permission.INTERNET" />
After that, the release APK connected to Firebase immediately.

Prompt 3: If you had more time, what would you improve?
I would add a dark mode toggle so it is easier on the eyes at night, and I would add 
a search bar at the top of the message board so you can filter messages by keyword 
or author name.

Prompt 4: How did you decide what is public vs private?
Privacy is simple:
- Private: Everything in users/{uid} (user ID, full name, role, registration date). 
  Only the person who owns the account can see or change this.
- Public: The message text and author's display name on the board. Any signed-in 
  user needs to see this so they can read the board.

Prompt 5: Why use server time instead of phone time?
A phone's clock can be set wrong, the user might be in a different timezone, or 
someone could intentionally change their phone clock to game the post order. 
FieldValue.serverTimestamp() lets Google's server set the time, so all messages 
appear in the honest, correct order for everyone.

Prompt 6: How would you keep this app fast as it grows?
Right now we load the messages list. If the app grows to 10,000 messages, loading 
them all at once would slow down the phone and cost a lot of database reads. 
To fix this at scale, we use .limit(50) or .limit(100) and load older messages 
only when the user scrolls to the top (pagination).
